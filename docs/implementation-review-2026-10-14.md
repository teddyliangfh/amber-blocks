# MVP 实现审查（2026-10-14）

结论：保留现有架构，先修交互集成和可靠性，再做儿童试玩。数学底层已有扎实验证，但目前测试不能证明手机上的整条体验成立。没有必要为了下一轮迭代重写项目或引入后端。

- `CI=1 pnpm lint`：失败。缺少 ESLint 配置及依赖，自动引导安装被 `ERR_PNPM_UNEXPECTED_STORE` 阻断；当前安装使用用户 Library 中的 pnpm store，执行环境选用了项目内 store。CLI 同时报告网络不可用。不能把 lint 当作已通过。
- 使用真实题库、core 命令与布局函数做脚本复现，验证组搬运后托盘重排、布局溢出、异常存档 ref。

## 优先修复

### 1. P1：搬出整组会制造虚假独立槽位，破坏托盘位置稳定性

位置：`src/blocks-ui/Stage.tsx:65–71`。

`looseSlots` 通过槽中当前的 `unitId` 判断槽位是否属于整组。整组被搬上工作台后，原槽的 `unitId` 变成 null，这些槽全部进入独立块列表；同时组本身仍保留一个托盘占位。于是同一组既保留组占位，又多出 N 个单块占位。

复现：390×600 舞台、ch1-n10、seed=5，初始有两个 5 组及两个单块，布局对象 4 个。搬出第一个 5 后变为 9 个，统一比例从 0.80 降至 0.55，留在托盘的另一个 5 也改变位置。ch1-n12 完成参考解后，5 个布局对象变为 22 个，触发横向溢出回退。

建议：题目开始时建立稳定的托盘对象与槽位映射，组成员槽永远不作为独立空槽显示。根据对象当前位置只改变占用状态，不改变布局对象集合。回归测试要验证未搬动伙伴的位置、比例不变。

### 2. P2：托盘缩放只检查宽度，没检查高度

位置：`src/blocks-ui/layout.ts:102–134`。

`rowsFor` 只判断行宽和行数；两行排布的真实高度是 `2 × tallest × cell × scale + gap`，但 tray 高度只有 `2 × cell`。两行单块在比例 1 时就超出 8px；两格高的 10 伙伴占一行，另一行再放伙伴时，会明显超出托盘。

复现：390×600 舞台、ch1-n11，初始比例为 1，托盘高 122px，排布总高 252px。ch1-n12 初始比例约 0.60，总高 154.4px，仍超出 122px。

建议：同时检查宽高，每行使用自己的最大高度，并将行间距纳入几何预算。若最低比例仍放不下，应调整舞台布局或内容材料，避免退回任由横向溢出。增加整个题库在多个手机尺寸与横屏尺寸上的边界检查。

### 3. P2：成功反馈重复，历史通关状态与本轮答案混用

位置：`src/screens/LevelScreen.tsx:108–120,242`；`src/progress/reducer.ts:complete`。

第一章数量题答对后，继续移动任意积木，数量仍正确，`update` 就再次触发庆祝和语音。`complete` 对已完成关卡返回成功，所以这里的 `r.ok` 不能表示“刚刚首次完成”。

此外 `solved = justMatched || completed` 会让历史通过的关卡在当前答案错误时仍显示绿色目标及“下一站”。进度可以永久保留，但当前答案反馈应独立。`replay`、`newVariant` 在领域层存在，却没有界面入口；当前地图点击完成站只是恢复作品。

建议：把历史已完成、当前 matched、本轮成功反馈是否已播放分开；反馈绑定明确的成功事件。提供“继续作品 / 重新挑战”，历史解锁保留，当前答案视觉按当前 verdict 显示。

### 4. P2：存储失败会白屏或产生未处理 Promise 拒绝

位置：`src/screens/progress-store.tsx:34–40,56,61–66`；`src/progress/store.ts`。

加载存储失败没有 catch，state 保持 null，而地图和关卡在此状态返回空白 View。写入失败被 `void save(...)` 忽略。每次提交会写整份进度，成功提交又立即写一次 complete；没有统一串行队列。原生异步适配器或未来适配器存在写入重排及 reset 与旧写入竞争的风险，这一项属于条件风险，本次没有复现真实设备的覆盖顺序。

建议：读取失败时进入可玩的内存模式，向家长提供轻量状态说明；写入经单一队列顺序处理，适度合并连续变更，reset 与队列协调。补充读写拒绝、延迟写入、重置竞争测试。

### 5. P2：存档校验只校验结构，未校验题目引用的一致性

位置：`src/progress/codec.ts:122–161`；`src/progress/migrate.ts:20–22`。

已复现：合法存档顶层 contentVersion 保持 1，只将一个 node 的 ref.contentVersion 改成 999。deserialize 接受，migrate 直接返回，进入关卡时 materialize 抛错。Map 的节点 key 与 ref.nodeId、chapterId、保存作品与题目材料之间也缺少交叉核验。

建议：恢复时验证节点存在、版本及引用一致、作品材料与该题相符。按节点丢弃损坏作品或引用，尽量保留语言与合法完成记录；关卡加载添加恢复界面，避免异常贯穿整个游戏。

## 产品与教学体验建议

1. **把整组点数补上。** `Stage` 只给 looseOnBench 的 UnitView 传 onTapUnit；benchPartners 没有点数回调，PartnerView 内部块也没有独立点击。第二章全部材料是组，第一章 10 / 12 / 17 的主要材料也在组内，无法逐块点数。整组拖动可以继续保持，但点击具体单位应能点数，或者提供明确的逐块点亮数总量动作。这是现有交互能力的缺口，不是把第二章单块拖动视作既定要求。
2. **加法成功后显示结果。** 标题一直是 `a + b`，合体后仍是两个有独立脸和数字的伙伴；结果主要依赖语音。建议成功时显示 `a + b = n` 或总量 n，并短暂逐块点亮，同时保留来源组颜色。无需自动把两组焊成一个不可拆的物体。
3. **帮助语按材料类型区分。** 当前“再拿一块 / 放回一块”也用于整组题，但整组材料不能取下一块。帮助应提示找哪个伙伴、拖回哪组，或说明“现在数量够了，再把它们接起来”。
4. **帮助更容易发现。** 四岁用户不一定会进入 ≡ 再选择“帮助”。建议保留简洁界面，把目标数字点击重播做成可见的喇叭提示，并在新题型首次出现时给短暂动作示范。先观察试玩，不引入长教程。
5. **允许重新点数。** CountRound 对同一材料集合只数一次，数满后继续点击被忽略；需要明确的“再数一遍”动作，无须搬走一块来重置轮次。
6. **地图定位当前关卡。** 两岛总高度超过 2000px，地图没有滚到当前站的逻辑；保留底部开始按钮，同时让返回地图时当前站进入视野。
7. **家长可选择章节。** 当前 17 Boss 是进入加法岛的必经条件。建议家长区可选择内容或跳过，不改变儿童主线默认顺序；避免把大数操作熟练度作为体验简单加法的前提。
8. **自由和文案边界。** “怎么分都行”目前实际只接受给定 allowed 中的两个组组合，并非任意块组合。建议说明“找两个伙伴拼出 5”，或扩大玩法；不要让提示承诺比判定规则更宽。

## 工程建议

- 保留 core / content / progress 的纯 TS 边界、稳定 UnitId、原子组移动、只在提交后判定、确定性题目生成和有界 undo。
- 把新增测试投入界面集成。当前约 98.6% 的行覆盖率统计排除了 Stage、手势 hooks、页面组件和 ProgressProvider，不能理解为整个应用达到同样覆盖。优先测试组取放位置稳定、过关后重排、恢复及重玩、切语言、取消拖动、存储失败。
- 真机检查 Safari 地址栏变化、横竖屏切换、拖拽中断、中英语音首次播放、添加到主屏幕后恢复。现有浏览器 mock 不能保证这些行为。
- 原生端当前明确使用 createSilentVoice；若下一阶段仍是手机网页，属于已知范围限制。开始原生交付时再补语音适配器。Expo SDK 58 已提供 Speech 模块，接入时以对应版本文档为准：https://docs.expo.dev/versions/v58.0.0/sdk/speech/ 。
- `package.json` 的 React Native 固定为 0.88.0-rc.4，后续发布前做 SDK 兼容性检查；不要在本次审查中盲目升级。模板依赖可逐项确认是否实际使用，减少维护负担，不以依赖数量直接推断 bundle 大小。
- 修好 lint 初始化，统一 pnpm / Node 版本与 store 配置；在 CI 连续跑 lint、typecheck、测试门禁、web export。
- README、PRD、spec 的状态存在矛盾（5 站 / 19 站、未开发 / MVP 完成、托盘一行 / 两行），整理“当前实现 / 已知缺口 / 未来方向”。减少后续开发按旧文档误改。

## 建议推进顺序

1. 修托盘对象稳定性、宽高约束、成功反馈；补界面集成回归。
2. 修存档恢复与错误处理，打通 lint；完成真机检查。
3. 补整组点数、可见加法结果、重玩与重复点数入口。
4. 用少数代表关卡陪孩子试玩，记录能否理解任务、抓到对象、主动点数和发现不同摆法，再决定扩题与正式美术。

本轮建议暂缓账号、云同步、复杂能力评分和大规模扩题。下一轮最有价值的结果是让孩子独立玩懂几道代表题，并在手机上稳定完成操作。
